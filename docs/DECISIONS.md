### ADR-0004 — Candidate PDFs are extracted by the Python worker, and everything derived from them lives outside every Git checkout
- **Date (UTC):** 2026-10-28
- **Proposed by / reviewed by:** Product Owner instruction (local training-data pipeline, Stage B) / independent review pending
- **PRD requirement IDs affected:** none. No requirement, task status or PRD checksum is touched.
- **Problem and alternatives:** `candidate:import` read `Resume*.docx` only, so a directory of candidate PDFs had no intake path at all. Alternatives: (1) parse PDFs in TypeScript with a Node PDF library — rejected: a second extractor means two sets of text, offsets and failure codes for one document, and the service's pdfplumber path is already proven by its own tests; (2) call the running FastAPI service — rejected: it returns one joined text with no page boundaries, and private intake must not depend on a listening process; (3) a new standalone pipeline — rejected outright: it would duplicate the fact lifecycle and the review gate.
- **Decision and rationale:** `services/ai/local_intake_cli.py` extracts a document into a private draft using `extract_text.pdf_page_texts`, which is the existing pdfplumber call split out of `extract_pdf` so page boundaries survive (`extract_pdf` is unchanged and still tested against the split). `src/candidate/pdf-intake.ts` re-verifies that draft — every line span is re-sliced in TypeScript, the text digest is recomputed, and `classifyDocument` must call it a resume — then hands it to the existing `buildPendingFacts`. One extractor, one taxonomy of extraction failures, one review lifecycle. Four conditions are reported instead of one exception, so a scan (`NEEDS_LOCAL_OCR`) is never confused with an empty document (`EMPTY_DOCUMENT`) or a two-column reading-order problem (`LOW_TEXT_CONFIDENCE`).
- **Private-data boundary:** drafts, extracted text, the id salt and PDF-derived pending facts are written only under `%JH_PRIVATE_ROOT%`, outside every working tree, enforced in both languages before any byte is read. `private-runtime/` stays valid for the owner's own `.docx` facts, whose behaviour is unchanged. A `.gitignore` rule is a one-line undo; a directory in no working tree cannot be staged at all.
- **Security, candidate consent and regression impact:** offline is the default and fails closed on a missing dependency; the in-process network guard is documented as a tripwire, not a boundary, with the Windows Firewall and `--network=none` options and their verification in `docs/privacy/LOCAL-PIPELINE.md`. Worker output is pseudonymous ids, status codes, counts and timings — no file name, no document text. `npm run ci:private-staged` blocks a commit that stages candidate data, including anything forced past `.gitignore`; the pre-commit hook is shipped but deliberately not installed. Every imported fact stays `pending` with null verification, and no duration, proficiency or role tag is derived.
- **Approval / reviewer:** Product Owner (scope: Stage B only, stop after). QA review pending.
- **Implementation commit / test evidence:** uncommitted on `feature/project-command-center`. `services/ai`: 148 passed, 1 skipped (36 new in `tests/test_local_intake.py`; 112 pre-existing, unchanged). TypeScript: `tests/candidate` + `tests/ci` 140 passed; full offline suite 1,517 passed with the DB suites skipped (PostgreSQL is not running) and the one documented `packet/build` flake (`docs/KNOWN_FLAKES.md`).
- **New PRD version and SHA-256 (if altered):** unchanged.

#### Amendment B.1 to ADR-0004 (2026-10-28, two-column reading order)
- **Failure investigated:** the two-column synthetic resume was rejected `NOT_A_RESUME`. Traced end to end: pdfplumber returns the page top-to-bottom across the gutter (`"EDUCATION SOC Analyst, Tier 1"`), so every line-anchored heading rule in `src/candidate/document-type.ts` missed. Measured `classifyDocument` scores — native text RESUME 4 (two `date-range` signals only, zero section signals) against `MIN_SCORE` 6, hence `NO_CLEAR_DOCUMENT_STRUCTURE` → UNKNOWN/REVIEW → `NOT_A_RESUME` in `loadIntakeDrafts`. The classifier was right to refuse it; the input was garbled.
- **Marker checked, as instructed:** `services/ai/.venv-marker` has marker 1.10.2 + torch + surya and runs offline here. On the same fixture Marker gets the column order right but merges lines (`"Incident triage EDUCATION"`, `"Umbral Defence Partners Security Analyst, Tier 2 May 2022 - Present"`), scoring RESUME 8 with one section signal out of three, at 16-22 s per document. The geometric rebuild scores 13 with three of three at ~20 ms and keeps one printed line per line, which is what `buildPendingFacts` reads. Marker stays the heavyweight path `batch_resumes.py` uses for the markdown/`resume_schema` pipeline; it was not adopted here.
- **Fix, and only there:** reading order in `app/local_intake.py`. `detect_column_gutter` now scores each candidate x per printed row — rows straddling it minus rows crossing it — because a page-height band of whitespace does not survive a full-width name banner, which nearly every real two-column resume has. `reflow_page` partitions rows, not words, and treats a row as two column entries only when its words leave a gap of at least 10 pt or 2% of the page width at the gutter. `document-type.ts` was **not** touched: no heading rule was loosened and no threshold lowered, so an uncertain document is still refused.
- **Guards on the rebuild:** a rebuilt page must hold the same non-whitespace characters as the extractor's own text for that page, or the rebuild is discarded (`REFLOW_REJECTED_CONTENT_MISMATCH`, status `LOW_TEXT_CONFIDENCE`, native text kept). Every line keeps `native_index`, `bbox` and `column`. Nothing is reordered inside a line, so a date cannot move between entries.
- **Contract versions:** `INTAKE_REVISION` `local-intake@1` → `@2`, draft schema `local-intake-draft/1` → `/2` (adds `readingOrder`, and `native_index`/`column`/`bbox` per line, `reading_order` per page). A reflowed document's canonical text differs from @1's, which is why both were bumped.
- **Measured on the 11 synthetic fixtures:** classification 11/11; printed section headings surviving as their own line 28/28; line span validity 126/126; of 24 emitted facts, 24/24 have a traceable locator whose span re-slices to a real line, and 24/24 quote their extracted field values from it. The composite `value` of an employment fact uses `" — "` where the page prints `" - "`, a pre-existing label-composition detail of `buildPendingFacts`; employer, title and dates are verbatim.
- **Known limits:** one gutter per page, so a two-up sub-block inside a column stays interleaved; a three-line employment entry (employer / title / dates on separate lines) still yields no employment fact, because the importer reads those from one line.
- **Tests:** `services/ai` 159 passed, 1 skipped (47 in `tests/test_local_intake.py`). TypeScript full offline suite 1,526 passed, 21 files skipped (PostgreSQL not running), 0 failed.

#### Amendment B.2 to ADR-0004 (2026-10-28, multi-line employment)
- **Looked first, as instructed.** `services/ai/app/parse_markdown.py` already reads employment across the layouts a resume uses: role and dates on one line, employer on the line above, employer two lines above a title above a date line, and either order of employer and title, choosing the title side by its keywords rather than by position. It has its own layout suite (`tests/test_markdown_layouts.py`, six layout cases plus an ambiguity case) and refuses rather than guesses (`EMPLOYMENT_ROLE_AMBIGUOUS`, `EMPLOYMENT_ROLE_MISSING`, `EMPLOYMENT_DATE_INVALID`, `EMPLOYMENT_INVALID`, `PLACEHOLDER_SKIPPED`). It was probed against the intake text of every fixture before anything was written, and read all of them correctly, including the three-line two-column entries and the LinkedIn export. **No new employment parsing rule was written.**
- **What was added:** `services/ai/app/employment_candidates.py`, a join of about 150 lines that runs that parser over the intake text, attributes each record to the page its evidence starts on, and carries the parser's refusals into the draft beside the records. The worker writes them under `employment`; `src/candidate/resume-import.ts` maps them to pending facts.
- **Alternatives rejected:** reimplementing the grouping in TypeScript (a second set of rules to keep in step with the tested one); switching the intake path to Marker (16-22 s per document, merges printed lines, and amendment B.1 already recorded why it is not used here).
- **Dates, and the contract that bites:** `candidate-profile.ts` requires `YYYY-MM` on an employment fact. A year-only start therefore cannot be represented, so the entry is **not imported** and is reported with its dates quoted verbatim; inventing a month to satisfy the schema was the one option ruled out. A year-only end with a month start keeps the start and records the end in `detail`. A month-level inversion inside one year, which the parser's year-level check cannot see, is refused per fact, so one bad record cannot fail a batch.
- **No double import:** a document carrying an employment reading skips the single-line rule, so a job is never imported by both. An identical entry in two documents of one batch stays one fact with a note naming the other, which is the pre-existing merge behaviour.
- **Evidence:** each record carries UTF-16 spans for the whole entry, the employer and the title. `verifyEmploymentSpans` re-slices all three against the draft text and also requires the employer and title strings to appear inside their own evidence; a draft that fails is not imported. Draft schema `local-intake-draft/2` to `/3` (adds `employment`); `INTAKE_REVISION` stays `local-intake@2` because the text, spans and pages are unchanged. The draft records the employment parser's own revision.
- **Measured over the 11 synthetic fixtures:** 13 of 13 printed employment entries imported with exact employer, title and dates (11 distinct facts; two entries printed in two fixtures merge by design), 0 spurious. The inverted-date entry (`Dunsmere Payments`, March 2021 to January 2019) stayed out and was reported as `EMPLOYMENT_INVALID`. Across all 29 facts: traceable locator 29/29, evidence present in the document 29/29, extracted field values quoted from that evidence 29/29, pending 29/29. Employment facts rose from 6 to 11, and classification, section coverage and span validity stayed at 100%.
- **Tests:** `services/ai` 178 passed, 1 skipped (19 new in `tests/test_employment_candidates.py`). TypeScript full offline suite 1,538 passed, 21 files skipped (PostgreSQL not running), 0 failed; `tests/candidate` plus `tests/ci` 158 passed.
- **Limits:** `EMPLOYMENT_DATE_INVALID` is unreachable from this path, because a line only anchors an entry when it holds a range the parser can already read; a test records that. Skills, projects, certifications and education still follow the owner's own template headings, so a resume that labels sections differently yields none of those.

#### Amendment B.3 to ADR-0004 (2026-10-28, candidate isolation for a multi-person corpus)
- **Defect found in pre-run validation, before any profile was opened.** `candidate:import` collects every document of a run into one profile and deduplicates across them, so a fact found in two documents becomes one fact with an "Also appears in" note. That is correct for one person's several resumes, which is what it was built for, and wrong for a corpus of unrelated people: measured on the Stage B.1 synthetic run, 5 facts had been merged across documents, and two candidates who had worked for the same employer would have shared a single employment fact.
- **Fix:** `--per-candidate --out-dir <dir>` writes one profile per document, each named by the document's own pseudonymous candidate id (derived from the source hash and the private salt, never from the file name). `buildPendingFacts` is called once per document, so the deduplication map lives inside that call and cannot span two candidates. Deduplication inside one candidate is unchanged, as is the default collect-into-one-profile behaviour. A profile that already exists is not overwritten without `--force`.
- **Regression tests (7, `tests/candidate/pdf-intake.test.ts`):** two candidates with byte-identical employment, skills and education stay two records with their own copies; no fact carries a merge note across candidates; every fact belongs to exactly one candidate while the same `factId` legitimately exists under both; within-candidate dedupe still collapses a repeat; an existing profile is not overwritten; `--per-candidate` without `--out-dir` is refused; and the default single-profile behaviour still merges with its note.
- **Verified on the synthetic corpus:** 11 drafts in, 4 refused as unusable (one scan, two empty, one unreadable), 7 profiles out, 7 distinct identities, 34 pending facts (employment 13, skill 18, certification 3), 0 approved. Employment rose from 11 to 13 against the merged run, which is exactly the two previously-merged duplicates returning to their own candidates.
- **Ingestion of the 20 authorized synthetic profiles did NOT run.** The owner's instruction was to stop if an OS-level offline boundary could not be verified. This session is not elevated, no `JobHunter*` firewall rule exists, and every profile's `DefaultOutboundAction` is `NotConfigured`, i.e. allow. The in-process guard is a tripwire, not a boundary (ADR-0004), so no PDF was opened.

### ADR-0005 — Integrated baseline: M5.1 is the trunk, project-command-center merges in with one true merge commit

**Status:** Accepted 2026-10-29 under the JH-REPO-001 standing approval (OWNER MAY VETO). ADR-0004 is reserved for the uncommitted candidate-PDF decision currently in the project-command-center working tree (ported in R2.5).
