Master ARD slice S1 (`docs/ard/Job-Hunter-Master-ARD-Architecture-Freeze.md`, section 6). Branch `careerops-integration`.
Environment: Windows 11, Node 24.13.1, Python 3.12.10 (dedicated venv), PostgreSQL 17.6 in Docker, Chrome (headed), 2026-10-09.
Nothing is committed. **S2 has not been started.**

All data in tests and fixtures is synthetic. No real resume, candidate fact, or employer site was used.

## What now exists

```
Astro UI (web/, 127.0.0.1:4321)  --same-origin /api proxy-->  Fastify API (src/api, 127.0.0.1:8787)
      sign in, upload, review, approve, edit, state sensitive facts          |   |
                                                                              |   +--> PostgreSQL 17 (Docker, 127.0.0.1:55440)
                                            Python FastAPI (services/ai, 127.0.0.1:8765) <--+      authoritative for S1 tables only
                                            PDF/DOCX text, rules parser, optional Qwen fallback (proposals only)
```

PostgreSQL is authoritative for the **S1 candidate workflow only**. The legacy JSONL jobs, structured jobs, decisions, checkpoints and
`private-runtime/candidate/*.json` profiles are untouched and still feed the existing pipeline. There is no dual writer: nothing writes
S1 data to JSONL, and nothing in the old pipeline writes PostgreSQL. A projection of approved PostgreSQL facts into the old profile
format was deliberately **not** built; it belongs to a separately tested cutover.

## Decision notes

* **D1 Authority split.** PostgreSQL authoritative for S1 tables; JSONL untouched; no dual writer; no projection yet. *Rollback:* stop the stack, optionally run the down migration; nothing else was changed.
* **D2 Rules first, Qwen only when required.** A small deterministic parser already recovers the structured resumes. A model is consulted only if the rules found no skill, employment or education fact, and only to return verbatim quotes that code verifies. Employment is never model-proposed (it needs dates). *Reversal:* leave `JH_AI_QWEN_FALLBACK=0` (the default).
* **D3 Offsets are UTF-16 code units** (the shared convention), converted in Python; verified with emoji text.
* **D4 Fact identity is scoped to a resume version** so identical text in two uploads stays two facts with separate provenance. Cost: no cross-resume dedupe in S1.
* **D5 Edits keep provenance and return the fact to pending** (matches the existing `applyFactReview`); approval is bound to the content digest the reviewer saw, so a stale click is refused (409).
* **D6 `citizenship` is its own fact kind** (additive to `FACT_KINDS`; existing profiles and digests are unchanged). `src/decision/evaluate.ts` previously checked a citizenship requirement against *work authorization* facts; it now uses citizenship facts. Result as decided by the owner: unknown or unverified => REVIEW; an approved, explicit "lacks" statement => FAIL => REJECT; a work-authorization fact never answers it. Sponsorship stays `record_only` and untouched. This is the one behavioural change to existing decision code; `tests/decision` covers it.
* **D7 Single-user local security model.** Access token from `infra/.env` => signed, expiring, HttpOnly, SameSite=Strict cookie; CSRF token derived from the cookie; Origin allow-list on every write; loopback Host check; no CORS; Python service needs its own bearer token. *Gaps:* the cookie is not `Secure` (plain HTTP on loopback); logout clears the cookie but a copied cookie stays valid until expiry (no server-side revocation); the login limiter is in memory.
* **D8 Extracted resume text is stored in PostgreSQL** (needed to show and verify source spans). It and the uploaded files (`private-runtime/s1-uploads/`, by content hash) are plaintext on this machine. Disk encryption is the owner's responsibility.
* **D9 No OCR.** A scanned PDF is a typed `NO_TEXT_LAYER` failure.

## Limitations and risks (read before relying on this)

1. **Parser quality on real resumes is unmeasured.** The 14 fixtures are synthetic and shaped like the rules. Multi-column or table layouts, DOCX headers/footers, non-English resumes, year-only dates (skipped with a warning), and unusual employer/title orders are known weak spots. The only protection is that nothing is ever auto-approved.
2. Employment `employmentType` is only set from an explicit `intern`/`co-op` keyword or by the reviewer; "professional" vs "academic" is a reviewer decision. S2 depends on that being filled in.
3. The profile revision digest covers *all* facts (pending too); the existing profile schema caps a profile at 2000 facts, beyond which reviews would fail.
4. The UI edits `value` for every fact but structured attributes only for employment. No manual "add a fact" except the four sensitive statements and contact kinds.
5. The client scripts in `web/` are transpiled, not type-checked (`astro check` is not installed); they are covered by the headed browser test.
6. `semgrep` and `pip-audit` are not installed here, so only `npm audit`, the repository's audit gate and manual review were done. One manual finding (unbounded chunked body in the Python service) was fixed and tested.
7. The development database `jobhunter` holds three synthetic smoke-test resumes and one approval from the manual smoke run, plus their files in `private-runtime/s1-uploads/` and a backup in `private-runtime/backups/` (all gitignored). They can be deleted; nothing else depends on them.
8. In CI, the DB, Python and browser suites skip themselves (no `infra/.env`, no venv, no `web/node_modules`); `ci.yml` was not changed, so CI does not yet exercise S1.
9. Not done on purpose: any job-discovery change, JD/Qwen/MiniLM pipeline change, resume generation change, form filling, submission, removal of JSONL records, major dependency upgrades.
