**Correction disclosed.** My first draft wrote "Experience with Splunk" / "Experience with Wireshark" / "Experience with Kubernetes or Terraform" and expected SUPPORTED. The matcher returned PARTIAL for Splunk. I checked the documented rule (docs/S4A-MATCHING.md line 37, config/jd-terms.v1.json: "experience with" is a demonstration cue; "familiarity" is a familiarity cue) and concluded the draft expectation had used the wrong wording class, not that the matcher was wrong. I changed the JD wording to the familiarity cue; I did not change an expected verdict to match output.

Assertions: the verdicts above; the OR group is SUPPORTED and Kubernetes and Terraform share its group id; Splunk `matchedFactIds` equals exactly the approved R1 fact id and contains neither the PENDING R2 Splunk id nor the PENDING Wireshark id (DB shows approved/pending/pending); the Wireshark requirement has empty support; the SUPPORTED card shows the exact JD quote "Familiarity with Splunk." and exactly one approved-evidence line "Your approved evidence (skill): Splunk"; no `%`, "match score", "hiring probability" or "ATS score" text; zero auto-apply/submit/apply-now controls; flag on the Wireshark card is recorded in `job_match_flags`. States: loading (gate loading view with a delayed response), empty (no saved postings), error (aborted API: gate shows the failure and Try again), and recovery through Try again; review/flag as above.

**Oracle bites.** `JH_ORACLE_FLIP=1` leaves the Splunk fact PENDING: the suite fails (Splunk UNSUPPORTED instead of SUPPORTED; the SUPPORTED card never appears), exit 1. Restored: 4/4 pass, exit 0.

**Root cause found on the way (fixed, test helper).** `freePort()` could return a port on the fetch/Chrome "bad ports" list (6667 happened); the Astro preview then never became reachable ("did not become reachable ... after 60000ms"). This is the likely cause of the one unexplained matches-ui failure in R6.2's parallel run. `tests/helpers/s1-harness.ts` now skips those ports.
